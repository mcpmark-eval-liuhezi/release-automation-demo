# Contributing to release-automation-demo

Thanks for helping out! This sandbox exists so you can practice the real workflow a
change goes through here before you touch a production repository.

## Getting set up

1. Fork the repository, then clone your fork locally.
2. Create a feature branch from `main` using a short, descriptive name
   (for example `docs/contributing-guide`).
3. Make your change in small, reviewable commits with clear messages.

## Proposing a change

1. Push your branch to GitHub and open a pull request against `main`.
2. Fill in the PR description: what changed, why, and how you tested it.
3. Request at least one review. Do not merge your own pull request; a reviewer
   with context on the area must approve it first.
4. Keep commits focused. When merging, maintainers squash the branch into a
   single commit so the history of `main` stays readable.

## Review expectations

- Reviewers leave comments pinned to specific lines rather than general opinions.
- Authors address feedback in follow-up commits so reviewers can see what changed.
- If a pull request goes stale, update it with the base branch before asking for another look.

## Reporting problems

Check open issues first so you do not file a duplicate, then open a new issue with
steps to reproduce it.
